投机解码

🚀 关键特性 · 11/22· 深入阅读约 15 分钟

本页的主线是算存比（arithmetic intensity, AI）： Decode 慢的根因是 LLM 在自回归阶段算存比极低，GPU 算力闲置而带宽打满； 投机解码（Speculative Decoding, SD）本质上是把闲置的算力换成更多的 token， 从而把单步推理推近 roofline 拐点。理解了这一点，就理解了从原始 SD 到 EAGLE-3 / Tree-Attention 所有"投机系"技术的统一框架。

Decode 为什么慢：算存比视角

设模型参数量 P，权重精度 b 字节（bf16 → 2, fp8 → 1）。 忽略 attention 部分，一次稠密前向对 n 个 token 的代价大致是：

资源消耗说明
HBM → SRAM 传输bytes ≈ P · b权重只被读一次，与 n 几乎无关
浮点计算FLOPs ≈ 2 · P · n每个 token 都要乘一遍权重
算存比AI = 2 · n / b FLOPs/byte仅与 n 和精度 b 相关

对于 bf16 模型，单 token decode（n=1）下 AI ≈ 1 FLOPs/byte。 作为对照——下面是主流 GPU 的计算/带宽比（即 roofline 拐点 AI*）：

GPU带宽 BWBF16 算力拐点 AI*
NVIDIA A100 80GB2.0 TB/s312 TFLOPS~156 FLOPs/byte
NVIDIA H100 SXM3.35 TB/s989 TFLOPS~295 FLOPs/byte
NVIDIA B2008.0 TB/s2250 TFLOPS~280 FLOPs/byte
AMD MI300X5.3 TB/s1307 TFLOPS~245 FLOPs/byte

结论：单 token decode 的 AI（≈1）比拐点 AI*（~150–300）低两个数量级。 GPU 的算力被严重浪费——这块"未用算力"，就是投机解码可以收割的红利。

投机解码如何把 AI 推到拐点

SD 的核心操作只有一个：让 target 模型在一次前向里同时验证 k+1 个位置 （k 个 draft 候选 + 1 个 bonus token）。从 roofline 看：

  • HBM 流量几乎不变（权重一次性读入，KV 多读 k 倍但量级远小于权重）；
  • FLOPs 线性增长 (k+1) 倍；
  • 因此 AI ≈ 2(k+1)/b，把工作点向右"平移" (k+1) 倍。

只要平移后仍在 memory-bound 区（即 k+1 ≤ AI*），target 的一次 forward 时间几乎不变，但一次前向却拿到了"1 + αk"个 token（α 为接受率）， 端到端 decode 吞吐线性提升。

定量：理论加速比

记单步加速比 S。在单流（batch=1）场景下：

朴素 decode 单步:       T_base ≈ P·b / BW
SD 单步 (k+1 位置):     T_sd   ≈ max( P·b / BW,            // 仍可能内存受限
                                    2·(k+1)·P / FLOPS ) // 推到拐点之后
SD 平均产出:            n_tok  = 1 + α·k
单步加速比 S = (1 + α·k) · T_base / T_sd

仅当 (k+1) < AI*      → T_sd ≈ T_base   → S ≈ 1 + α·k   (理想情形)
当   (k+1) ≥ AI*      → T_sd 随 (k+1) 线性增长 → S 见顶并下滑

再把 draft 成本 T_d ≈ k · P_d · b / BW 计入（P_d = draft 参数量）：

S = (1 + α·k) / ( 1 + T_d / T_base )
  ≈ (1 + α·k) / ( 1 + k · P_d / P )

对常见组合做个估算：

TargetDraftkα（典型）理论 S
Llama-3.1-70BLlama-3.2-1B（同家族）50.65(1+3.25)/(1+5/70) ≈ 3.96×
Llama-3.1-70BLlama-3.2-1B30.65(1+1.95)/(1+3/70) ≈ 2.83×
Llama-3.1-70BMistral-7B（跨家族）50.30(1+1.5)/(1+35/70) ≈ 1.67×
Qwen-2.5-72BEAGLE head（≈0.3B）50.75(1+3.75)/(1+1.5/72) ≈ 4.65×

实测落地通常是理论值的 40%~70%（kernel launch、tree 验证、采样开销等）， 对应大模型 decode 1.5×~3× 的端到端加速。

与 batch / 连续批处理的相互作用

真正部署时是持续高 batch 的：target 一步同时跑 B 条请求，每条又携带 k+1 个位置， 拐点位置就变成 AI* / (k+1) 处的有效 batch。简化结论：

有效 batch B·(k+1)所处区域SD 的边际收益
< AI*（远小于）Memory-bound免费的 (1+αk) 倍 ← 甜区
≈ AI*拐点附近仍正收益，但边际递减
> AI*（远大于）Compute-boundSD 反而变慢（多算 k 倍 FLOPs）

这就是为什么——

  • 低 QPS / 在线对话：SD 最划算；
  • 极高吞吐压测（B 很大）：SD 可能关掉反而更好；
  • 混合场景：vLLM 可以按当前 batch 自适应调整 k（draft 数）。

基本流程与无损保证

sequenceDiagram participant D as Draft 模型(小) participant T as Target 模型(大) D->>D: 自回归生成 k 个候选 token t1..tk + draft 概率 q D->>T: 把 [前缀, t1..tk] 一次前向 T-->>T: 对每个位置算 target 概率 p Note over T: 从左到右用重要性采样接受/拒绝 T-->>D: 接受 m 个 token (0≤m≤k), 第 m+1 个 token 按修正分布重采样

接受规则（Leviathan / Chen, 2023）

对位置 i，draft 给出概率 qi(x)，target 给出 pi(x)。 对 draft 输出的 token ti：

接受概率: r_i = min(1, p_i(t_i) / q_i(t_i))
若拒绝: 从 残差分布 max(0, p_i - q_i) / Σ_x max(0, p_i(x) - q_i(x)) 中重采样一个新 token
之后位置丢弃，下一轮重新 draft。

可证明：经过这个规则得到的整条序列分布 = 直接用 target 自回归生成 的分布。 即 SD 是数学上无损的——温度、top-p、top-k 等所有采样参数都仍适用。

为什么"无损"很重要？

不像量化（精度损失换吞吐），SD 是纯加速。你不需要单独评估 "开启 SD 后下游指标是否退步"——只需关心是否真的快了。

从线性候选到 Tree Attention

朴素 SD 让 draft 给出一条直线 的 k 个候选。 现代 SD 让 draft 给出一棵树——每个位置上保留 top-r 个分支， target 用定制的 tree attention mask 在一次前向里同时验证所有分支。

flowchart LR Prefix --> A1[t1=a] Prefix --> A2[t1=b] A1 --> B1[t2=ax] A1 --> B2[t2=ay] A2 --> B3[t2=bz] B1 --> C1[t3=axp] B1 --> C2[t3=axq] B2 --> C3[t3=ayp] B3 --> C4[t3=bzr]

好处：

  • 同一个 batch slot 内可以保留多个路径，有效接受率显著提高（α 从 ~0.4→0.7+）；
  • 多走的算力仍在 memory-bound 甜区之内——相当于把 k 横向扩成树宽 ×深度；
  • vLLM V1 的 spec_decode 实现就是 tree-aware 的（EAGLE-2/3 默认开启）。

代价是 attention mask 变得稀疏不规则——需要 FlashAttention / FlashInfer 的 tree-mask 内核支持。

三句话总结技术演化

  1. 2023 年：参数/算力上动——独立小模型 / n-gram，最早证明 SD 可工程化。
  2. 2024 年：结构上动——Medusa/EAGLE/Hydra 把 draft 缩成"target 的几层附件"， Tree Attention 把候选从一条线扩成一棵树。
  3. 2025 年：形状与训练目标上动——EAGLE-3、Sequoia、Online SD 用动态树形 / 动态规划 / 在线学习把"算力预算 ↔ 接受率"的取舍做到接近极限。

vLLM 中的实操

启用与配置

# A) 独立小模型（最通用、零门槛）
vllm serve meta-llama/Llama-3.1-70B-Instruct \
  --speculative-config '{
    "model": "meta-llama/Llama-3.2-1B-Instruct",
    "num_speculative_tokens": 5
  }'

# B) N-gram / PLD（零额外权重，适合代码补全、模板化输出）
vllm serve <target-model> \
  --speculative-config '{
    "method": "ngram",
    "num_speculative_tokens": 5,
    "prompt_lookup_max": 4,
    "prompt_lookup_min": 2
  }'

# C) EAGLE / EAGLE-3（吞吐最高，需要单独训练好的 head）
vllm serve <target-model> \
  --speculative-config '{
    "method": "eagle3",
    "model": "<eagle3-head-checkpoint>",
    "num_speculative_tokens": 5,
    "draft_tensor_parallel_size": 1
  }'

# D) Medusa（target 自带 medusa head 的 checkpoint）
vllm serve <medusa-aware-model> \
  --speculative-config '{
    "method": "medusa",
    "num_speculative_tokens": 4
  }'

字段说明调优经验
num_speculative_tokensk：每轮 draft 候选数对话 3–5、代码 5–8；先小后大

监控指标

在 /metrics 端点能看到：

  • vllm:spec_decode_num_accepted_tokens / num_emitted_tokens → 计算接受率 α；
  • vllm:spec_decode_draft_acceptance_rate（按版本而异）；
  • vllm:time_per_output_token_seconds 在开启前后对比；
  • vllm:num_requests_running 用于推断当前有效 batch。

调优 checklist

从小到大、按指标决策
  1. k=1 试水：验证管道通了；
  2. 看接受率：< 30% 直接换 draft（更同源 / 改用 EAGLE）；
  3. 看 TPOT：开启后比 baseline 下降才有意义；
  4. 看 batch：用 disable_by_batch_size 防止高并发下倒贴；
  5. k 扫 1,3,5,7：找到本工作负载的 sweet spot；
  6. Tree 方法下，num_speculative_tokens 是树深度， 树宽由 method 自身控制（EAGLE 系列默认动态）。

常见误区与排障

"高 batch 压测下吞吐反而降了"

不是 bug，是物理规律——见上面"与 batch 的相互作用"。解法： 设 disable_by_batch_size，或对在线/离线两种流量分开起两套 vLLM。

"接受率怎么也上不去"

常见原因：(1) 跨家族 draft（tokenizer/分布差太多）；(2) 创作 / 高温度场景（每个 token 都有多种合理选择，draft 难命中）；(3) 模板没对齐（chat template 用错）。 对策：换同家族 draft 或上 EAGLE；高温度时把 k 调小至 2–3；务必检查 tokenizer.eos_token_id 一致。

"显存变紧"

Draft 模型占额外显存。粗算 P_d × b 字节。EAGLE/Medusa 的 head 一般 <1 GB； 独立 1B–7B draft 需要预留几个 GB。可同时降 --gpu-memory-utilization 给 SD 留预算。

"和量化叠用"

SD 与权重量化（AWQ/GPTQ/FP8）正交——理论上能叠。但要注意：量化压低了 T_base， 相对收益会缩水（因为 T_base 本来就小了，SD 的"省"占比变小）。 实测 FP8 + EAGLE-3 仍能在 1.5–2× 区间。
