RoPE 旋转位置编码

🧠 核心原理 · 附加 / 深入· 阅读约 18 分钟

本页解答两个问题：

  1. 位置信息如何"旋转进"语义向量？——讲清楚 RoPE 把 token 嵌入两两配对当作复数、按位置乘上一个旋转因子的全过程；
  2. RoPE 与 KV Cache 怎么配合？——澄清 K 是旋转后才写入缓存，这一选择带来的所有连锁结果（解码不再重算 RoPE、Prefix Cache 仍能命中、长上下文为何需要 YaRN/NTK 等扩展）。

讲解一律配上 vLLM 仓库的源码引用，并在末尾做一次"自查迭代"列出本页与其他 Wiki 页之间的潜在矛盾点。

动机：为什么需要位置编码

原始 Transformer 的 self-attention 对 token 顺序是置换不变的—— 打乱 [A, B, C] 顺序，每个位置上的 Q·Kᵀ 内积值都不变，模型完全"看不出"顺序。 位置编码（Position Encoding, PE）的工作就是把序号注入到向量里，让 attention 区分先后。

方案形式问题
绝对正弦 PE（原始 Transformer）给嵌入加上 sin/cos 序列向量外推差、相对位置不显式
可学习 PE（BERT）每个位置一个可学习向量超出训练上下文就 OOD
相对位置 PE（T5/Shaw）attention 里加偏置项 b(i−j)实现复杂，影响 kernel
ALiBiattention logits 上加线性距离衰减表达能力受限
RoPE（Su et al. 2021）把 Q/K 视为复数 按位置旋转—（事实标准）

RoPE 之所以"赢"，三个原因：(1) 不增加参数，(2) 内积自然只依赖相对位置， (3) 改个公式即可外推到更长上下文。Llama 全家、Qwen、DeepSeek、Mistral、ChatGLM 全用 RoPE。

核心思路：把维度两两配对当复数

记 token 在第 i 层、第 h 个 head 上的 query 向量是 q ∈ ℝd（d 为 head_dim，必须是偶数）。 RoPE 的做法：

  1. 把 q 的 d 个分量两两配对，形成 d/2 对： (q0, q1), (q2, q3), …, (qd−2, qd−1)。 每一对当作一个二维复平面里的向量 zk = q2k + i·q2k+1。
  2. 对第 k 对，给它一个频率 θk。
  3. 当这个 token 处在位置 m 时，把第 k 对乘上 ei·m·θk ——即在复平面上旋转 m·θk 弧度。

用实数 2D 旋转矩阵写出来就是：

flowchart LR subgraph one[第 k 对维度] A["(q_2k, q_2k+1)"] end R["乘上 2×2 旋转矩阵 R(m·θ_k)"] A --> R --> B["(q'_2k, q'_2k+1)"] 
R(α) = | cos α   -sin α |
       | sin α    cos α |

(q'_2k    )   ( cos(m·θ_k)  -sin(m·θ_k) ) ( q_2k    )
(q'_2k+1 ) = ( sin(m·θ_k)   cos(m·θ_k) ) ( q_2k+1 )

对 key 向量做完全一样的操作（同样的 θ 频率族）。这就是全部。

直观图像

想象 head_dim=64：你把这 64 维拆成 32 个二维平面。每个平面上有一个"指针"（向量）。 位置 m 把第 k 个平面的指针逆时针转 m·θk 弧度。 转完之后再用旋转后的指针参与 attention。

频率族 θk 的设计

RoPE 的频率族延续了原始 sinusoidal PE 的"几何序列"思路。设旋转维度 D = head_dim （或 partial RoPE 下的 rotary_dim），基底（base，常用 10000）：

θ_k = base^(-2k / D),   k = 0, 1, ..., D/2 - 1

  → θ_0 = 1.0           (最高频, 一个 token 转 1 rad)
  → θ_{D/2-1} ≈ 1/base  (最低频, 几乎不转)

对应到 vLLM 源码（vllm/model_executor/layers/rotary_embedding/base.py）：

def _compute_inv_freq(self, base: float) -> torch.Tensor:
    inv_freq = 1.0 / (
        base ** (
            torch.arange(0, self.rotary_dim, 2, dtype=torch.float) / self.rotary_dim
        )
    )
    return inv_freq

这就是 θk 列表。然后预先算好 每个绝对位置 m × 每个 θk 的 cos、sin 查表，避免在线 sin/cos：

def _compute_cos_sin_cache(self) -> torch.Tensor:
    inv_freq = self._compute_inv_freq(self.base)
    t = torch.arange(self.max_position_embeddings, dtype=torch.float)

    freqs = torch.einsum("i,j -> ij", t, inv_freq)   # [max_pos, D/2]
    cos = freqs.cos()
    sin = freqs.sin()
    cache = torch.cat((cos, sin), dim=-1)             # [max_pos, D]
    return cache

缓存形状 [max_position, rotary_dim]，前一半 cos、后一半 sin。 后续所有 token 在所有层共享这一张表——RoPE 既不增加可训练参数， 运行时也只多了一次 O(N·d) 的 elementwise 操作。

为什么是几何分布的频率？

  • 低频维度负责"远距离"：θ 很小，几百上千个 token 累积下来才转完一圈， 适合表达"开头这段话是什么领域"这类长程关系。
  • 高频维度负责"近距离"：每隔一个 token 就转半圈，适合"刚刚那个词是不是动词"这类局部关系。
  • 几何分布让模型在 O(log L) 个尺度上都能区分位置——和 multi-scale wavelet 同思路。

关键性质：内积只依赖相对位置

这是 RoPE 最重要的数学性质，也是它"用绝对旋转、得相对位置"的奥秘。

设位置 m 处的 q' 是 Rm·q，位置 n 处的 k' 是 Rn·k （其中 Rm 是把 m·θ 旋转打包成的块对角矩阵）。 内积 (q')T(k')：

(R_m q)^T (R_n k) = q^T R_m^T R_n k = q^T R_{n-m} k

           (因为旋转矩阵 R_m^T = R_{-m}, R_{-m} R_n = R_{n-m})

也就是说：attention 分数 (q', k') 只通过 Rn−m 依赖于"相对位置 n−m"， 与 m、n 各自的绝对值无关——这正是相对位置编码梦寐以求的性质， RoPE 却用"对每个 token 单独绝对旋转"轻松拿到。

这条性质带来的工程好处
  1. Q、K 旋转完后可以直接走标准 dot-product attention 内核， 不需要为相对位置写特殊 kernel。FlashAttention/FlashInfer 直接受益。
  2. 位置信息不污染 V——V 完全不被 RoPE 触碰，attention 输出仍是原始的 value 加权。
  3. 对解码而言，每生成一个新 token，只要把"它的 q、k"按其位置 m 转一下； 历史 K 不必重算（因为它们的旋转已经在它们当时被写入 KV Cache 时完成）。

NeoX 风格 vs GPT-J 风格

"维度两两配对"有两种顺序，社区里两派并存：

风格配对方式使用模型
GPT-NeoX style
(is_neox_style=True)		 把向量拆成"前半 / 后半"，第 k 维与第 k+D/2 维配对 LLaMA 全家、Qwen、Mistral、DeepSeek
GPT-J style
(is_neox_style=False)		 相邻偶/奇下标配对（k 与 k+1） GPT-J、ChatGLM 早期、GGUF llama 某些导出

两种风格数学等价，但内存布局不同——错配会得到一个被"打乱"的 K， attention 输出像噪声。vLLM 用一个布尔参数同时支持，源码（common.py）：

def apply_rotary_emb_torch(x, cos, sin, is_neox_style: bool) -> torch.Tensor:
    cos = cos.unsqueeze(-2).to(x.dtype)
    sin = sin.unsqueeze(-2).to(x.dtype)
    if is_neox_style:
        x1, x2 = torch.chunk(x, 2, dim=-1)           # 前半 / 后半
    else:
        x1 = x[..., ::2]                              # 偶数下标
        x2 = x[..., 1::2]                             # 奇数下标
    o1 = x1 * cos - x2 * sin
    o2 = x2 * cos + x1 * sin
    if is_neox_style:
        return torch.cat((o1, o2), dim=-1)
    else:
        return torch.stack((o1, o2), dim=-1).flatten(-2)

注意公式 o1 = x1·cos − x2·sin、o2 = x2·cos + x1·sin—— 完全对应前面贴的 2D 旋转矩阵。

CUDA 内核走查

性能关键路径在 csrc/pos_encoding_kernels.cu。核心是一个 "每个 thread block 处理一个 token、并行覆盖该 token 的所有 head × 旋转对"的内核：

template <typename scalar_t, bool IS_NEOX>
inline __device__ void apply_token_rotary_embedding(
    scalar_t* __restrict__ arr,
    const scalar_t* __restrict__ cos_ptr,
    const scalar_t* __restrict__ sin_ptr,
    int rot_offset, int embed_dim) {
  int x_index, y_index;
  scalar_t cos, sin;
  if (IS_NEOX) {
    // 前半 / 后半 配对
    x_index = rot_offset;
    y_index = embed_dim + rot_offset;
    cos = VLLM_LDG(cos_ptr + x_index);
    sin = VLLM_LDG(sin_ptr + x_index);
  } else {
    // 偶 / 奇 配对
    x_index = 2 * rot_offset;
    y_index = 2 * rot_offset + 1;
    cos = VLLM_LDG(cos_ptr + x_index / 2);
    sin = VLLM_LDG(sin_ptr + x_index / 2);
  }
  const scalar_t x = arr[x_index];
  const scalar_t y = arr[y_index];
  arr[x_index] = x * cos - y * sin;   // 同一个 2D 旋转
  arr[y_index] = y * cos + x * sin;
}

启动方式：每个 token 一个 block，block 内多线程并行处理 num_heads × embed_dim 个标量对——一次 forward 整个 batch 的 Q、K 都在一个 launch 里转完。这是纯 elementwise，几乎完全 memory-bound， 比起后续的 GEMM 与 attention 来说耗时可忽略。

在模型层是怎么被调用的

以 vllm/model_executor/models/llama.py 的 attention 块为例（节选）：

# 一次 forward：
qkv, _ = self.qkv_proj(hidden_states)
q, k, v = qkv.split([self.q_size, self.kv_size, self.kv_size], dim=-1)

q, k = self.rotary_emb(positions, q, k)   # ← RoPE 在这里就地修改 q、k

attn_output = self.attn(q, k, v)          # ← K、V 在 self.attn 内部
                                          #   被写入 KV Cache 并参与 attention
output, _ = self.o_proj(attn_output)

核心是 self.rotary_emb(positions, q, k)——它在 attention 之前 把 Q、K 就地旋转好。positions 是一个一维 LongTensor，长度 = 本步要算的 token 数， 每个元素是该 token 在所属 sequence 内的绝对位置。 对连续批处理来说，这个张量里同一个 batch 不同请求的 token 各有各的 position， 内核拿 positions[token_idx] 去查 cos_sin_cache。

这是 vLLM 与"按 batch padding 推理"框架的关键区别之一

传统实现是 [batch, seq_len] 矩形的 positions（每条 seq 0..L−1）， RoPE 内核因此要按 batch 维度 broadcast。vLLM V1 把所有 batch 拍平成 [num_tokens]，每个 token 自带它的位置—— 这与 连续批处理 是一体化的设计。

RoPE 与 KV Cache 的协作（核心连接）

这是本页第二个主问题。要把 RoPE 与 KV Cache 之间的关系彻底说清楚， 关键就一句话：

K 是旋转之后才写入 KV Cache 的；Q 每次都重算，不缓存。

对比一下推理时一个新 token 进入 attention 的流程：

flowchart TB H[hidden_state\n本步新 token] --> QKV[Wq, Wk, Wv 投影] QKV --> Q[q_new] QKV --> K[k_new] QKV --> V[v_new] Pos[positions[token_idx]] --> Rot[RoPE 旋转] Q --> Rot K --> Rot Rot --> Qr[q' rotated] Rot --> Kr[k' rotated] Kr --> Cache[(KV Cache\n写入 k', v_new)] V --> Cache Cache --> Attn[Attention\nq' · K_cache^T / √d · V_cache] Qr --> Attn Attn --> Out

为什么"存旋转后的 K"是正确选择

方案缓存什么每步成本分析
vLLM 实际（业界主流）旋转后的 K（已带位置）仅对"新 token"做 RoPEO(1) 旋转 + 直接 attention
朴素方案 A旋转前的 K每步都要把历史所有 K 重新旋转O(L) 额外开销 / 步，长上下文不可接受
朴素方案 B缓存 hidden_state，每步重做 QKV+RoPE每步重做 O(L) GEMM退化为无缓存

选 A 还有一个看似不严重、实际很麻烦的代价——长上下文扩展（YaRN / Dynamic NTK 等）让 "位置 m 怎么旋转"依赖于本次推理所声明的 max_seq_len。 缓存"未旋转 K"等于把这个决策延后到 attention 内部，所有 attention kernel 都要重写支持 RoPE 内联。 而缓存"旋转后 K"则把 RoPE 隔离在 attention kernel 之外——这是个干净的解耦。

对 Prefix Caching 有什么影响

vLLM 的 Prefix Caching 以"块（block）"为单位、对 "截至此处的 token 序列"做哈希。RoPE 是纯函数—— 同一段 token 序列在同样的起始位置 0..N 下产生同样的旋转后 K，因此

  • 同一个 system prompt + 同样的工具描述：所有用户进来都命中前缀块；
  • 同一段对话的多轮：旧消息那部分 K 仍然命中（它们的位置没变）；
  • 把同一段文本插到不同位置：旋转结果不同 → 不复用 → 这是正确的行为， 不是 bug（因为位置不同时 attention 分数本就该不同）。
什么时候 Prefix Cache 会"看着像命中却没命中"

(1) 长上下文扩展配置变了（rope_scaling 的 type / factor / max_pos 改了） → cos_sin_cache 重算 → 即使 token 序列一样，旋转结果也变了。这种情况建议清空 Prefix Cache。

(2) 切了不同的 dtype（bf16 vs fp16）→ cos_sin_cache 精度位模式不同， 极端情况下 block hash 不一致。

那 Q 呢？

Q 永远是"本步新出现的 token 的"——历史 Q 与未来都无关，无需缓存。 每步对新 Q 旋转一次（O(1) 开销）即可。

Partial RoPE 与 head_size 不等于 rotary_dim

有些模型并不把 head_dim 全部旋转，而是只对前 rotary_dim 维做 RoPE， 后面那段保留原样（"NoPE"段）。源码里有专门处理：

query = query.view(num_tokens, -1, head_size)
query_rot  = query[..., :rotary_dim]      # 要旋转的部分
query_pass = query[..., rotary_dim:]      # 直接透传
query_rot  = apply_rotary_emb_torch(query_rot, cos, sin, is_neox_style)
query = torch.cat((query_rot, query_pass), dim=-1)

典型例子：

  • Phi-3 / Phi-3.5：partial_rotary_factor < 1，前段旋转后段保留。
  • DeepSeek-V2/V3（MLA）：把 K 拆成"压缩 latent"（无 RoPE）+ "解耦小段"（有 RoPE）， 这是把 RoPE 与 KV 压缩两件事彻底解耦的巧思——见 deepseek_scaling_rope.py。

长上下文 RoPE 家族

RoPE 的频率族最初按"训练时见过的最大长度"设计。当推理时 token 位置超过这个范围， 高频维度会迅速旋转到混乱区——模型外推 OOD。 2023–2024 年涌现一组"长上下文 RoPE"方案，全部在 vLLM 中有实现：

方案vLLM 文件核心 idea使用模型
Linear PI（Position Interpolation） linear_scaling_rope.py 把位置 m 缩放成 m/s（s = 扩展倍数），相当于"压扁 RoPE 频率" 早期 Llama-2 扩展
NTK-aware ntk_scaling_rope.py 不缩位置，改基底 base→base·sD/(D−2)，让高频维度少变化 各种社区 fine-tune
Dynamic NTK dynamic_ntk_scaling_rope.py / dynamic_ntk_alpha_rope.py 训练时不动，推理时按当前实际 seq_len 自适应放大基底 Qwen 部分版本
YaRN（Yet another RoPE extensioN） yarn_scaling_rope.py 对不同频率分段处理：低频按 PI 缩、高频按 NTK 放，再加全局温度修正 Yi、Qwen-2.5 长上下文
Llama-3 RoPE llama3_rope.py 类似 YaRN 思路的频率分段，参数从 HF config 读 Llama-3.1+
Phi-3 LongRoPE phi3_long_rope_scaled_rope.py 用搜索得到的逐维缩放因子表，short/long 两套配置切换 Phi-3-mini/medium long
DeepSeek MLA RoPE deepseek_scaling_rope.py 仅对 K 的"解耦小段"做 YaRN 风格扩展 DeepSeek-V2/V3
Dual-Chunk RoPE dual_chunk_rope.py 把长序列分块，块内用一种 RoPE，块间用另一种 ChatGLM-2 等
MRoPE（Multimodal RoPE） mrope.py 把"位置"扩展成 3D 元组 (t, h, w)，分别在不同维度上转 Qwen2-VL / 2.5-VL（视频）
xDRoPE / Llama-4 Vision RoPE / ERNIE-4.5 VL RoPE xdrope.py / llama4_vision_rope.py / ernie45_vl_rope.py 各家多模态 / 长上下文的私有变体 各自模型

这些方案都通过修改 cos_sin_cache 的内容实现， "RoPE 怎么旋转"只与 cache 表的具体数值有关，下游 attention 代码完全不变—— 这正是"缓存旋转后 K"那个架构选择带来的红利。

性能优化：融合内核

RoPE 本身轻量，但它夹在 QKV projection 与 attention 之间， 每层都要做一次 elementwise pass、读写一遍 Q/K 整张。在 decode 阶段（memory-bound）这是额外的 HBM 流量。vLLM 用两类融合压低开销：

  • Fused QK-Norm + RoPE：QwenX、Llama-4 风格在 RoPE 前还会对 Q、K 做一次 RMSNorm， vLLM 把"QKV split → QK norm → RoPE"融成一个 kernel—— csrc/fused_qknorm_rope_kernel.cu 与 vllm/compilation/qk_norm_rope_fusion.py。 Q/K 只走一遍 HBM。
  • FlashInfer 的 in-place RoPE：与 attention 同模块的旋转实现， 对 head_size ∈ {64, 128, 256, 512} 做了特化。详见 base.py 中的 flashinfer_rotary_embedding 自定义算子注册。

常见陷阱

"换了 Llama 风格 RoPE，输出全是乱码"

多半是 is_neox_style 弄反了。Llama 系列必须 NeoX， 某些社区 GGUF 导出可能是 GPT-J 风格。vLLM 会按模型类型自动选， 自己改代码时务必两边对齐。

"长上下文模型在 vLLM 里效果不如 HF transformers"

大概率是 rope_scaling 配置没被正确读到。检查模型 config.json 是否带 rope_scaling = {"type": "yarn", "factor": 4.0, ...} 之类， 并在 vLLM 启动日志里搜 "rotary" 看实际生效的实现类。

"自定义模型 head_dim=80 跑不起来"

有些 FlashAttention / FlashInfer 后端要求 head_dim ∈ {64,128,256,...}， 与 RoPE 不直接相关，但 RoPE 必须 head_dim 偶数（因为要两两配对）， 奇数 head_dim 直接不合法。

"K 是旋转过的，能直接做 FP8 量化吗？"

可以。FP8 KV Cache 量化（--kv-cache-dtype fp8_e4m3）发生在 RoPE 之后、写入 cache 之前；解码时反量化回 bf16/fp16 参与 attention。 RoPE 的旋转幅值不会让数值范围超出 FP8 表达能力（仍是 ±|K| 量级）。

再次过本页论述，检查可能的错误或过度简化：

  • ✅ "K 是旋转后写入 cache"——源码 llama.py 里 q, k = self.rotary_emb(...); self.attn(q, k, v) 已证实， self.attn 内部把已旋转的 k 交给 cache writer。
  • ✅ 内积只依赖相对位置——前提是 q、k 用同一组 Rm。这点 vLLM 是满足的 （同一 RotaryEmbedding 实例同时旋转 q 与 k）。
  • ⚠ "几乎不增加显存"——cos_sin_cache 占 max_position × rotary_dim × dtype， 对 Llama-3.1 长上下文（max_pos=131072, dim=128, bf16）约 32 MiB。不影响功能但应被知道。
  • ⚠ "RoPE 不损推理质量"——前提是训练与推理使用同一套 base/扩展方案。 擅自给 base 模型套 YaRN 而不微调，会有质量下降。
  • ⚠ 本页避开了"为什么 base=10000"的玄学；这是 sinusoidal PE 沿用值， 且与 head_dim 配合下覆盖几个数量级位置。这是经验值。
