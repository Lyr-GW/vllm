CUDA Graph & torch.compile

⚡ 性能 · 16/22

问题：Kernel Launch 开销

Decode 阶段每生成一个 token 都会触发几十到上百个 CUDA kernel launch。 每次 launch 在 CPU↔GPU 之间有几微秒的延迟；在小 batch / 短 seq 下， 这部分开销可能占总时间的 30%+。

CUDA Graph 是什么

CUDA Graph 把一段"已经知道形状"的计算流"录像"成一个 graph 对象。 之后可以用一次 cudaGraphLaunch 把整段重放，跳过逐 kernel 的 host 提交开销。

flowchart LR A[首次执行: capture] --> B[CUDAGraph 对象] B --> C[后续相同形状: replay] C --> D[GPU 上批量执行所有 kernels]

vLLM 怎么用

  1. 启动时，针对一组预先选定的 batch 大小（如 1, 2, 4, 8, ..., 256）预捕获 decode 阶段的 graph。
  2. 运行时，按实际 batch 找到最接近的"桶"，pad 到该桶大小后 replay。
  3. Prefill 阶段形状变化太大（每条 prompt 不同长度），默认不用 graph。

关键开关：

开关说明
--enforce-eager完全禁用 CUDA Graph，调试 / 老硬件时用
--cuda-graph-sizes自定义要捕获的桶大小
--compilation-config更细粒度的 compile + cudagraph 配置（V1）

torch.compile 集成

V1 中 vLLM 大量使用 torch.compile 把 Python 层 fuse 到 Inductor / Triton 内核， 进一步减少 op overhead，并启用 fusion（如 RMSNorm + ResidualAdd + Quantize）。 启动时会看到"Capturing compile graph"之类日志——这是首次启动的一次性开销， 缓存命中后非常快。

动态 shape 怎么办

因为 graph 录的是固定形状，vLLM 用以下策略适配动态：

  • Bucketing：把"实际 batch size 13"映射到"捕获的桶 16"，多 pad 3 个空槽位。
  • 多桶 capture：默认捕获 ~30 个常见大小，覆盖 1..最大并发。
  • fallback to eager：超出最大桶 / 启用某些不兼容特性时退回到 eager 模式。

什么时候关掉 graph

  • 调试一个 reproducible 的报错（graph 的错误堆栈不友好）；
  • 使用一些尚未兼容的特性（如某些前沿采样器、自定义 logits processor 操作了 Python 状态）；
  • 启动时间敏感（捕获要时间）：--cuda-graph-sizes 1 8 只捕几个桶。

实操影响

  • 开启 graph 后，低并发 下 TPOT 通常下降 20%~40%。
  • 高并发下收益变小（kernel 大、launch 占比下降）。
  • 关闭 graph 时建议同时 --enforce-eager，避免半启用状态。
