DeepSeek V4 与 1M 上下文

🔬 进阶专题· 阅读约 20 分钟

本页要点

DeepSeek 在 2026 年 4 月 24 日发布了 DeepSeek-V4，两个开源 MoE 变体（V4-Pro 1.6T / V4-Flash 284B）都原生支持 1M token 上下文。其核心创新是用 CSA + HCA 混合稀疏注意力替代 V3 的 MLA， 让 1M 上下文在显存与算力上都可负担。本页解答三个问题：

  1. "1M 上下文"指的到底是什么的 1M；
  2. 怎样在工程上把这个 1M 实现出来；
  3. 与 KV Cache、RoPE 的关系。

"1M 上下文"指什么

当一个 LLM 声明支持 N-token 上下文，N 是单次推理时 prompt + 生成结果合计的最大 token 数。 对 DeepSeek-V4：

  • 1,048,576 token（= 220，约 75 万汉字 / 一本中长篇小说）；
  • 是原生支持——训练阶段就经过 1M 长上下文的微调， 不是靠 YaRN/NTK 等推理期外推硬撑；
  • 它是单个请求的总 token 数上限，包含：system prompt、user 消息、tool 调用结果、模型已生成的 token。

"1M" 不是指：

  • ❌ 训练语料长度（V4 训练涉及的总 token 远超 1M，那叫 dataset size）；
  • ❌ 跨请求记忆（vLLM/任何主流引擎都不会跨请求共享 hidden state）；
  • ❌ KV Cache 容量（KV 容量由显存 + 量化 + 压缩共同决定，1M 是 attention 可看到的窗口）。

为什么"把 N 调到 1M"这么难

给一个 LLM 加 1M 上下文，工程上至少撞三堵墙：

瓶颈朴素 attention 下的规模具体痛点
Attention 计算复杂度O(L2) FLOPsL=1M → 比 L=128K 多 60× 的 FLOPs，prefill 几小时
KV Cache 显存O(L) 线性增长Llama-3-70B 风格 GQA-8 + bf16，1M token 占 ~160 GB/请求
位置编码外推RoPE 频率族在训练范围外混乱需要 YaRN / 长 RoPE 或重新训练

DeepSeek-V4 同时解决了前两个：用稀疏 + 重压缩注意力替代密集 MLA。 第三个则靠"训练时直接喂长样本"+ 部分 RoPE 这种工程手段。

DeepSeek 长上下文技术演化时间线

timeline title DeepSeek 注意力机制演化（关注 KV/长上下文） 2024-01 : DeepSeek-V2 引入 MLA\n（KV cache 低秩压缩） 2024-12 : DeepSeek-V3 + V3.1\n（MoE 规模化 + MLA 精细化） 2025-12 : DeepSeek-V3.2 引入 DSA\n（Lightning Indexer + top-k 稀疏 MLA） 2026-04 : DeepSeek-V4 引入 CSA/HCA\n（4× 与 128× 双压缩混合层）

从 V2 到 V4，DeepSeek 在 attention 上反复迭代的方向是同一个： 不要再让 KV cache 与 attention 计算量随 L 线性增长。 理解 V4 之前先快速过 MLA 和 DSA。

MLA：V2/V3 的低秩 KV 压缩（基石）

朴素 GQA/MHA 每个 token、每层、每个 KV head 都要存 (K, V) 共 2·H_kv·d_h 个浮点数。MLA（Multi-head Latent Attention）的做法是： 把 KV 投影到一个低维 latent 子空间存起来，attention 时再上投回原维度。

朴素 MHA:    K, V ∈ R^{B × L × H_kv × d_h}
            KV cache 每 token = 2 · H_kv · d_h · b 字节

MLA (V2/V3): 把 (K, V) 共同压成 latent c_t ∈ R^{r_kv}   (r_kv ≪ H_kv·d_h)
            KV cache 每 token = r_kv · b 字节
            attention 前: K_t = W_uk · c_t, V_t = W_uv · c_t

DeepSeek-V3 典型: r_kv ≈ 512, H_kv·d_h ≈ 16384  → 32× 压缩
                 加 RoPE decoupled 段 (k_R ∈ R^{r_R}, r_R ≈ 64)

关键点：RoPE 不能直接套在 latent 上（旋转矩阵会和 W_uk 缠在一起，破坏共享）。 V2 的方案是把 K 分成两段——非 RoPE 部分走 latent 压缩，RoPE 部分单独保留一小段、 不压缩、按位置旋转。这是上一页 RoPE 里提到过的"DeepSeek decoupled RoPE"。

MLA 把 V3 在 128K 上下文的 KV cache 压到与 Llama-3 GQA-8 相当的水平， 但到了 1M 上下文仍然不够——线性 O(L) 累计起来依旧难承受。

DSA：V3.2 的稀疏 MLA

V3.2-Exp (2025-12) 提出 DeepSeek Sparse Attention (DSA)： 不是再压 K/V 本身，而是让每个 query 只 attend 到 top-k 个最相关的 KV。

flowchart LR Q[Query q_t] --> Idx KVcache[(全 L 个\n压缩 KV)] --> Idx subgraph IdxBlock[Lightning Indexer] Idx[低秩 q/k 投影\n+ LayerNorm + RoPE\n→ 多头点积打分] end Idx --> Top[Top-K=2048\n选择器] Top --> Attn[只对 2048 个 KV\n做完整 attention] Attn --> Out[h_t]

关键设计：

  • Lightning Indexer 是一个轻量的 quasi-attention 头，作用是给"全 L 个 KV 块"打分。 它有自己独立的小 K 缓存（indexer K cache），与主 KV cache 分开存储。
  • Top-K=2048 选择器在 L=128K 下只保留 2048 个最相关 KV—— 密集 attention 部分就从 O(L²) 退化为 O(L·2048)。
  • V3.2 论文报告：128K 上下文下相比密集 MLA， prefill 成本 3.7×、decode 成本 7.2× 的下降。

V4 的核心创新：CSA + HCA 混合注意力

V4 把 DSA 思路推到了下一步：不再做"全长 KV cache + 稀疏选择"， 而是从源头就把 KV 沿序列维度压缩（pooling），然后在压缩后的序列上做注意力—— 有两种压缩等级，交替放在不同层。

CSA — Compressed Sparse Attention（4× 压缩 + 稀疏）

核心步骤：

  1. 软门控池化（softmax-gated pooling）：在序列维度上用 有重叠的窗口把每 4 个相邻 token 的 K、V 合成 1 个池化条目； 门控权重由 softmax 学出，不是简单 mean pool；
  2. Lightning Indexer (FP4 + ReLU 多头点积)：在已经被 4× 压缩的池上为每个 query 打分；
  3. 取 top-k 个压缩块送入主 attention，做完整的 softmax(QKᵀ)V。

由于稀疏选择前 KV 已经 4× 缩短，搜索空间就小了 4 倍；indexer 跑在更低精度（FP4）也更便宜。 CSA 层负责"远距离但仍要保细节"的依赖。

HCA — Heavily Compressed Attention（128× 压缩 + 致密）

HCA 走另一条路：

  1. 无重叠 128× 池化：把每 128 个 token 的 K、V 直接合成 1 个池化条目；
  2. 不需要 indexer——压缩后序列已经很短（1M token → 仅 ~8K 池化条目）， 可以承担致密 attention；
  3. 每个 query 与所有压缩条目做完整 softmax(QKᵀ)V。

HCA 是"全局粗粒度"通道——它读不了"第 327,891 个 token 是什么字"， 但能稳稳掌握"这 1M token 的整体语义脉络"。

三种 attention 的混合编排

层类型视野分辨率典型作用
Sliding-window full attention 本地 sliding_window 长度逐 token Bootstrap 层 + 局部细节
CSA（4× 压缩，稀疏 top-k） 全 1M 上下文每 4 token 一块 远距离 + 细节兼顾
HCA（128× 压缩，致密） 全 1M 上下文每 128 token 一块 全局语义脉络

这三种 attention 在 V4 的层堆里交替编排，每个 token 在不同层得到多分辨率的远近混合视野。 和 wavelet / pyramid 网络的思想同源——但工程上做到 1M 上下文级别。

V4 的共享组件（所有 attention 层公用）

组件解释
Shared K=V Multi-Query Attention MQA（只 1 个 KV head），且 K 与 V 用同一组投影——KV cache 再减半
Partial RoPE（interleaved-pair） 只对 head_dim 的末尾段做 RoPE，采用 GPT-J 风格的相邻偶/奇配对（不同于 Llama 的 NeoX 风格）
Per-head learnable attention sink 每个头有一个可学习的"虚拟 KV 锚点"，借鉴 StreamingLLM 的 sink-token，但学习而非固定
Grouped low-rank output projection
DeepseekV4GroupedLinear		 把 num_heads × d_h → hidden 的稠密 GEMM 拆成 head 组、再过低秩 bottleneck，参数与 FLOPs 都缩
Shared sliding-window K=V branch 稀疏层旁挂一个 sliding-window 的"快路径"，保 fine-grained 局部能力
Manifold-Constrained Hyper-Connections (mHC) 用多条并行残差流 + 双随机矩阵投影替代单一加法残差，缓解 Pre-Norm 在极深网络下的协方差漂移
Hash-based MoE bootstrap 最前面几层用固定 token_id → expert_id 哈希查表，避免初期 router 训练不稳

1M 上下文下的实际显存账

这是用户问"和 KV cache 有什么关系"的直接答案。引用官方与 HuggingFace 博客的数字：

对照1M 上下文 KV cache1M 单 token decode FLOPs
BF16 GQA-8 baseline（Llama-3 风格 70B 类）100% (≈ 几百 GB)100%
DeepSeek-V3.2 (MLA + DSA)~50% 一档取决于 top-k
DeepSeek-V4-Pro (1.6T MoE) ≈10% of V3.2，≈2% of GQA-8 BF16 ≈27% of V3.2
DeepSeek-V4-Flash (284B MoE) ≈7% of V3.2 ≈10% of V3.2

这个"2%"是怎么来的？把各步压缩链乘起来就清楚：

                              cache per token
GQA-8 BF16   (baseline)        H_kv·d_h·b · 2 = 8 · 128 · 2 · 2 ≈ 4 KB
MQA (shared K=V)               ÷ 8 (head)  · ½ (K=V 共享) →   ~250 B
Pool 4× / 128× (CSA / HCA)     再 ÷ 4 ~ 128, 按层加权平均 →   ~80 B
   ↓
对 1M token:                  ~80 MB / 请求 / 层
  ↓ 几十层
V4-Pro 一个 1M 请求的总 KV    数 GB ~ 十几 GB 量级

对比 BF16 GQA-8 baseline 一个 1M 请求需要几百 GB——根本装不下。 V4 之所以能把 1M 真正交到用户手上，本质是把"每 token 缓存几 KB"压到"每 token 缓存几十字节"， 而压缩点是 多个：MQA、共享 K=V、池化、低 bit。

用一句话总结

V4 的 1M 上下文 不是靠"扩大 KV cache"，恰恰相反——是靠 "用更少的 KV 表达更长的上下文"。CSA/HCA 让 attention 在压缩后的、更短的 KV 流上运作， KV cache 物理大小与 1M 上下文之间不再是线性关系。

与 RoPE / Prefix Caching 的相互作用

RoPE 部分

  • V4 用 partial RoPE（interleaved-pair = GPT-J 风格），只对每个 head 的末尾若干维度旋转—— 这与 Llama / Qwen 默认的 NeoX 风格不同；vLLM 加载 V4 时会按模型 config 选对 is_neox_style=False（详见 RoPE 页）。
  • 因为 KV 在写入缓存前要先池化、再做或不做 RoPE，旋转操作的"应用点"会和 V3 不同—— 池化后的代表 token 才被赋予位置，而不是逐 raw token 旋转后再池化。

Prefix Caching 部分

  • vLLM 的 Prefix Cache 按 token 块哈希。 V4 的"4× / 128× 池化 + 软门控"意味着同一段 prefix 在不同后文里池化结果可能不同 （重叠窗口的 softmax 门控对邻居敏感），尤其 CSA 层。 所以严格意义上 V4 上"前缀复用"的命中粒度变小——这是 1M 上下文的代价之一。
  • HCA 层（无重叠 128× 池化）受影响更小，因为同一段 token 在窗口对齐时池化结果是确定的。

在 vLLM 中部署 V4

截至本页撰写时，HuggingFace transformers 已合入 V4 支持 （docs/source/en/model_doc/deepseek_v4.md），vLLM 通过 transformers backend 跟进。 启动参数会和 V3 类似，但要注意：

vllm serve deepseek-ai/DeepSeek-V4-Flash \
  --tensor-parallel-size 8 \
  --max-model-len 1048576 \
  --gpu-memory-utilization 0.92 \
  --kv-cache-dtype fp8_e4m3 \
  --enable-prefix-caching \
  --enable-chunked-prefill

要点：

  • 必须开 chunked prefill——否则一条 1M prompt 一次性 prefill 会霸占整个 GPU 几十分钟。 建议同时调大 --max-num-batched-tokens（如 32768）让 chunk 不至于过碎；
  • KV 量化叠加：V4 自身已经做了序列维度压缩，KV bit 量化（fp8）仍可叠加再降 2×；
  • 显存仍要预留：即便 V4-Flash 在 1M 下 KV ≈ 7% of V3.2，单请求也要几 GB； 并发若干条 1M 时合计仍可观；
  • 抢占 / Swap：对 1M 请求几乎从不该走 Swap（IO 时长不可接受）， 应优先用 Recompute + Prefix Cache 命中尽量减少重做。

常见误区

"1M = 可以塞 1M 后端无影响"

错。即使 KV 大幅压缩，indexer + 池化 + 多层 GEMM 在 1M 长度下仍是几十秒 ~ 几分钟的 prefill。 TTFT 与 1M 几乎线性。HCA 的优势是每 token decode 时间， 不是 prefill 时间。

"V4 取代了 MLA"

V4 的 paper / blog 描述里，CSA / HCA 本身仍是 MLA 系下的变体—— KV 在通道维度仍走低秩 latent，只是再叠加了序列维度的池化与稀疏选择。 把它理解为"序列维稀疏 + 通道维低秩 + MQA + 共享 K=V"四件套同时启用更准确。

"V4 出来后 V3.2 的 DSA 就过时了"

不见得。DSA 不池化原始 KV、不丢失逐 token 分辨率， 对"需要精确逐 token 检索"的任务（精确 quote、代码逐字 reference）依旧有价值； V4 用更激进的池化换更长的上下文，是另一种权衡。

"1M 上下文 ≠ 1M 个 token 都同等重要"

V4 的 CSA/HCA 隐含一个工程信念：1M 个 token 中真正需要"逐字精确召回"的是少数。 对绝大多数 agentic 工作流（长会话、工具调用日志、检索文档）来说：

  • 近端几千 token 需要逐字精确（→ sliding-window full attention 处理）；
  • 中端十万级 token 需要细节但不必逐字（→ CSA 4× 压缩 + top-k）；
  • 远端百万级 token 需要"知道有这事 + 大致意思"（→ HCA 128× 致密压缩）。

这种"按距离分配带宽"的设计哲学，与人类记忆的层次非常像。 长上下文 LLM 从此从 "用更大的 KV cache" 转向 "用更聪明的 KV cache"。
