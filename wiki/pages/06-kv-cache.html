KV Cache 与 Prefix Caching

🧠 核心原理 · 6/22

KV Cache 的真实形状

在每个 transformer 层里，Self-Attention 会算出 K、V 两个张量。推理时不会重算历史 token 的 K、V， 而是把它们追加到一个长 buffer 里——这就是 KV Cache。在 vLLM 中：

每层 KV Cache 形状（简化）
  K: [num_blocks, block_size, num_kv_heads, head_dim]
  V: 同上 (有的后端布局略不同)

总显存 ≈ 2 × num_layers × num_blocks × block_size
        × num_kv_heads × head_dim × dtype_size

num_blocks 是由 vLLM 启动时通过"profile run"估算出来的—— 它先用一个假 batch 把模型跑一遍，测出非 KV 之外的显存峰值，剩下的空间全部切成 block 用作 KV Pool。 这就是 --gpu-memory-utilization 的语义来源。

核心数据结构

  • BlockTable：每条 sequence 一份，是个 int 数组，索引 = 逻辑块号，值 = 物理块号。
  • KVCacheManager（V1）/ BlockManager（V0）： 维护空闲块池、分配 / 释放 / 共享。
  • HashIndex：把"前缀 token 序列"映射到对应的物理块，是 Prefix Caching 的关键。

Prefix Caching 的工作流

很多场景下，多条请求共享前缀：

  • 同一个 system prompt；
  • 多人在调同一份知识库的 RAG，前面挂了相同的检索结果；
  • 同一对话的多轮，旧消息内容完全一致。

自动 Prefix Caching 的策略是按块哈希：

  1. 当 prefill 完成一个块（即 16 个 token）时，对"截至此处的全部 token"算一个 hash。
  2. 把 hash → physical_block 存进字典。
  3. 新的请求 prefill 之前，按 block 边界查表：命中则直接把 block_table 指向该物理块， 跳过这部分的 attention 计算。
flowchart LR Req1[请求 A 的 tokens 0..47] Req2[请求 B 的 tokens 0..47 与 A 一致, 48..95 不同] subgraph Phys[共享物理块] B0[Phys #10 (hash=h0)] B1[Phys #11 (hash=h1)] B2[Phys #12 (hash=h2)] end Req1 --> B0 & B1 & B2 Req2 --> B0 & B1 & B2 Req2 -.-> NewB[Phys #20 (B 私有新块)]

命中率高时，prefill 阶段几乎不花时间，TTFT 显著降低。

淘汰策略

当 KV Pool 满了，需要释放一些块。V1 中的策略：

  • 正在跑的 seq 持有的块不可释放；
  • 已完成 / 离线的 seq 的块进入可回收池；
  • 可回收池按 LRU + 引用计数挑出最不可能复用的块归还到空闲池。

因此 Prefix Cache 命中率不是 0/100：常用前缀活在 cache 中很久；冷门一次性 prompt 用完即丢。

Hybrid KV Cache Manager（V1）

不是所有层都用同一种 KV。例如：

  • Mamba / SSM 层用 state 而非 KV；
  • Sliding Window Attention 只需要一个窗口内的 K/V；
  • Multi-head Latent Attention（DeepSeek-V2/V3）需要 latent 缓存而非常规 K/V。

V1 的 kv_cache_interface.py 让每层把"自己需要的缓存形状"告诉引擎， manager 据此统一分配，因此 vLLM 可以同时承载混合架构。

命令行 / API 控制

开关含义
--enable-prefix-caching / --no-enable-prefix-caching启停自动前缀缓存（V1 默认开）
--block-size每块容纳的 token 数
--kv-cache-dtypeauto / fp8_e4m3 / fp8_e5m2：用 FP8 缩小 2× 显存
--gpu-memory-utilization预占比例，间接决定 num_blocks
--swap-space允许 swap 到 CPU 内存的容量（GiB）

调优建议

  • 稳定的 system prompt 一定要利用 Prefix Cache——它免费给你巨大的 TTFT 改善。
  • KV 量化 FP8：模型能用 fp16 跑时，KV 用 fp8 通常几乎无损（参考 FP8-E4M3），显存减半。
  • 不要随便调大 block_size：会减少前缀命中粒度。
  • 看不到 cache 命中？ 检查指标 vllm:prefix_cache_hit_rate。
