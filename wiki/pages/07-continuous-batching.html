连续批处理 & Chunked Prefill

🧠 核心原理 · 7/22

为什么不能像训练那样批处理

训练时一个 batch 内的样本通常等长（或 pad 到等长），一次前向所有样本同步进行。 推理则完全不同：

  • 每条请求到达时间不同；
  • 每条请求prompt 长度不同；
  • 每条请求生成长度不同；
  • 每条请求可能早停（遇到 EOS / stop string）。

用"等齐再批"或"按最大长度 pad"都会浪费 GPU。Continuous Batching（也叫 iteration-level scheduling） 的核心思想是：以单步 forward 为单位调度——每一步开始前，重新挑选一组 sequence 上 GPU。

Iteration-level 调度示意

sequenceDiagram participant T as 时间步 participant B as 批 (本步) Note over T,B: t=0 入: A(prompt=200), B(prompt=10) T->>B: t=1 prefill A,B Note over T,B: t=1 入: C(prompt=4) T->>B: t=2 decode A,B + prefill C T->>B: t=3 decode A,B,C Note over T,B: t=3 B 命中 EOS, 离开 T->>B: t=4 decode A,C Note over T,B: t=4 入: D T->>B: t=5 decode A,C + prefill D

这就是 vLLM 的引擎主循环长成的样子：调度器决定本步"谁继续 decode、谁新加进来做 prefill"， 然后把这一批喂给 worker 跑一次前向。

prefill 与 decode 的差别

阶段计算特点GPU 角色
Prefill对 prompt 一次性算 K/V，sequence 长度 = prompt 长度compute-bound（矩阵乘很大）
Decode每步只算 1 个新 token，需要把所有历史 K/V 都参与 attentionmemory-bound（搬 KV 是瓶颈）

没有 chunked prefill 时，一个超长 prompt 进入会"霸占"GPU 整整一步： 其他 sequence 的 decode 全部要等它 prefill 完才有机会上车。 体验上就是：长 prompt 一来，整个集群 TPS 卡顿一下。

Chunked Prefill

解决方案是把长 prompt 切成多个 chunk，每个 chunk 与正在 decode 的其他 sequence 混在同一步里跑。这样：

  • 正在生成的 sequence 不会被卡住，TPOT 更平滑；
  • 同一步内同时有 prefill 的"大块矩阵乘"和 decode 的"小批 attention"，GPU 利用率更高。
flowchart LR subgraph S[一个超长 prompt, 4096 tokens] P0[chunk #0\n0..1023] P1[chunk #1\n1024..2047] P2[chunk #2\n2048..3071] P3[chunk #3\n3072..4095] end Step1[Step k] -->|P0 + decodes| GPU Step2[Step k+1] -->|P1 + decodes| GPU Step3[Step k+2] -->|P2 + decodes| GPU Step4[Step k+3] -->|P3 + decodes| GPU

每步的 token 总数受 --max-num-batched-tokens 限制。给定该上限， 调度器会把 prefill 的剩余 token 与 decode 的当前 token "凑"到上限。

关键参数

参数说明
--enable-chunked-prefill启用（V1 默认开）
--max-num-batched-tokens每步 token 上限。值越大，prefill 越快但 decode 受影响
--max-num-seqs每步并发序列上限，影响 batch 大小
--scheduling-policyFCFS / priority 等

常见误区

"开了 chunked prefill 反而变慢？"

把 --max-num-batched-tokens 设得太小（如 512）会让 prefill 被切得太碎， 矩阵乘变小、kernel launch overhead 占比上升。一般保持默认或基于工作负载用 benchmark_serving.py 扫一遍。

"为什么我看到 TPS 比官方数字低？"

官方数字通常是持续打流下的稳态吞吐。短时启动、缓存未热（Prefix Cache 没命中）、 或 client 串行发请求都会低估。请用 benchmark_serving.py --request-rate ∞ 来测稳态。

它怎样与 PagedAttention 协作

Continuous Batching 之所以能用一个 kernel call 跑一个混合 batch（不同 seq 不同长度）， 正是因为 PagedAttention 不再要求 K/V 连续。 两者是 vLLM 的"双引擎"，缺一不可。
