调度器与执行循环

🧠 核心原理 · 8/22

它在哪

  • V0：vllm/core/scheduler.py
  • V1：vllm/v1/core/sched/scheduler.py

调度器是引擎每一步开始时调用的"裁判"：选择本步要执行的 sequence、给它们分配 KV block。 它有一个最重要的方法 schedule()，返回一组 SchedulerOutput， 让 worker 据此构造批次。

三态队列

  • WAITING：到达但还没分到 KV 块的请求（多半因为显存暂时不够）。
  • RUNNING：正在被引擎处理的请求。
  • SWAPPED（V0）：被抢占后 KV 块换到 CPU 的请求。V1 中合并到统一的"被抢占待恢复"语义。
stateDiagram-v2 [*] --> WAITING WAITING --> RUNNING: 显存够 / 块够 RUNNING --> RUNNING: 每步推进一个 token RUNNING --> PREEMPTED: 块紧张 / 高优请求抢占 PREEMPTED --> RUNNING: 恢复 RUNNING --> FINISHED: EOS / stop / max_tokens FINISHED --> [*]

每一步在做什么

  1. 统计当前已用 / 空闲 KV 块。
  2. 遍历 RUNNING 序列：每条预估本步需要 1 个 token 槽（decode）或 N 个 token 槽（chunked prefill）。
  3. 如果总需求超过空闲，进入抢占路径：按优先级 / FIFO 选若干 RUNNING 退出。
  4. 把 WAITING 队列里能塞进剩余预算的请求拉上来 prefill。
  5. 构造本步的 SchedulerOutput：每个 seq 的 token_ids、新分到的 block ids、是否是 prefill。

抢占：Recompute vs Swap

当资源不够，调度器必须"让某些 seq 暂时下车"。它有两种处理方式：

策略含义代价
Recompute丢弃该 seq 的 KV Cache，下次恢复时整段 prompt 重做 prefill。重算时间
Swap把 KV 块从 GPU 拷到 CPU 内存（--swap-space），恢复时拷回来。PCIe 带宽

当 prompt 短、上下文短，Recompute 更划算；prompt 长则 Swap 更划算。V1 中 Swap 不是默认行为， 具体策略由 preemption_mode 控制。

优先级与公平性

vLLM 默认按 FCFS（先到先得）。但你可以：

  • 在 API 层为请求带 priority（高优会被优先调度，必要时抢占低优）；
  • 使用请求级别的最大上下文 / 最大生成长度限制， 防止单个长请求长期占用大量 KV 块；
  • 结合 Data Parallelism（多 engine 副本）把流量分到多个实例。

与 KV Manager 的协作

调度器只回答"本步要跑谁"，不直接管 K/V 怎么放。它向 KV Manager 询问"为这条 seq 多要一个块"， manager 返回新块号或 None（满了）。这样的解耦使两者都可以独立替换：

  • Manager 在 V1 中重写为 kv_cache_manager.py，支持 hybrid layout；
  • Scheduler 在 V1 中重写为单一的 Scheduler 类（不再区分 prefill / decode 两个 scheduler）。

实操影响

  • 你看到 vllm:num_preemptions_total 飙高？说明并发 / 上下文太大，调小 --max-num-seqs 或 --max-model-len。
  • 稳定开 Prefix Cache 能让被 Recompute 的请求恢复时秒到——因为它的前缀块大概率还在缓存里。
  • 用 --scheduling-policy priority 时，给在线流量打高优、批量任务打低优，体感会平稳很多。
